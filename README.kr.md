# MBQ, Merge based and Majority Quorum BFT Protocol.

## 목적
- 이 프로토콜은 합의 알고리즘에서 과반의 쿼럼만으로 비잔틴 환경에서의 안정성을 확보하고, 
비잔틴 합의를 관측의 교환, 위조 불가능한 서명, 그리고 동기 통신 가정으로 해결한 프로토콜이다.

## 가정
- 비잔틴 노드는 크래시, 네트워크 장애, 타임아웃, 일부 또는 전체 침묵, 이보케이션, 거짓된 요청, 담합등의 행위를 할 수 있다.
- 통신 환경은 동기 환경으로 가정한다.
- 이 알고리즘은 오직 합의 문제만 다룬다. Fail recovery는 구현체단에서 책임진다.
- 비잔틴과 크래시, 옴미션 가능 노드의 갯수는 f개, 정직 노드의 갯수는 f+1로, 총 2f+1개의 노드로 구성된다.
- 클라이언트의 정상 요청도 경우에 따라 실패 가능하지만 재시도로 성공 가능하다.
- 재시도 정책은 클라이언트의 책임이다.
- 클라이언트는 항상 정직하며 비잔틴이 될 수 없다 가정한다.
- 모든 노드와 클라이언트는 위조될 수 없는 서명을 할 수 있다.
- 클라이언트와, 서버가 항상 1:1로 맺어지는 IP Hashing등의 Load Balancing 규칙은 이 방법에 적절치 않다.
- Unknown은 비잔틴 여부와 관계가 없다.
- 서명은 위조 불가 하다.
- 같은 클라이언트 요청은 오직 한번만 커밋 된다.
- 클라이언트 요청 재시도는 구현체의 책임이며, 이는 로그에서 같은 요청이 있는지 대조하는식으로 멱등성을 보존해야한다.
- 거짓 실패(False Failure)이 발생 가능하며, 이에 대한 정책은 클라이언트 책임이다. 이는 이전 합의와 연관 없는 새 합의를 시작하게 한다.
- 서명은 자신의 모든 메시지를 담아 서명을 한다. 이 서명은 다른 단계나 요청에 재사용 될 수 없다.
- 페이지의 종료는 모든 노드들의 응답이 오거나 타임아웃이 발생했을때로 정의 된다. 페이지 종료 이후 추가로 온 요청은 인정치 않는다.
- 한 합의는 하나의 클라이언트 요청만을 담당한다.
- 커밋단의 커밋 인증서 서명은, 구현체에 따라 안정성이 보존되는 한에서, Threshold등으로 구현하여 최적화 할 수 있다.

## Phases
### Propose
```
    Propose(clientId, request, requestSignature) -> (proposeId)
```
- 프로포즈를 한 노드는 이번 합의의 프로포저가 된다.
- 이 단계에선, 클라이언트한테 받은 요청을 다른 노드들에게 넘기는 작업이다.
- 프로포저는 모든 노드에게 응답을 받으면 (timeout을 포함한다) 다음 페이지로 넘긴다.
- 한 노드가 다른 노드들에게 전파함으로 시간복잡도는 O(n)이다.

### Prepare
```
    Prepare(proposeId, sentRequest, isRequestSignatureValid, Signature) -> (sentRequest, isRequestSignatureValid, Signature)
```
- 이 단계에선 각각의 노드들이 자신이 프로포저에게 받은 값과 그 시그니처의 벨리드 여부를 교환한다.
- 이 단계 이후에선, 노드는 자신이 받은 값과 다른 노드들이 관측한 값을 가지게 된다.
- 주장이 이 노드에게 생성되었다는 증거물인 시그니처도 준다. 이는 이 노드가 이 값을 생성했다는 증거물이다.
- 한 노드는 한 합의당 무조건 하나의 유효한 서명이 생성되어야 하며, 두개 이상의 유효한 서명을 생성하는것은, 이보케이션으로 간주한다.
- 항상 시그니처를 받으면 검증하며, 만약 Propose를 받지 못 했다만 옳은 클라이언트 서명을 포함한 Prepare을 받으면 합의에 참여하게 된다. 자신의 주장은 Unknown이다.
- Propose를 못 받았던 노드들은 올바른 클라이언트 서명을 가진 Prepare을 받으면, 이후 단계에 참여하게 된다.
- 모르는 프로포즈에 대한 프리페어의 응답에 대해서는 항상 Unknown을 반환 한다.
- 시간 복잡도는 O(n^2)이 된다.

### Merge
```
    Merge(proposeId, {clientId:[request, isRequestSignatureValid, prepareSignature]}, ...) -> ({nodeId: {clientId:[request, isRequestSignatureValid, prepareSignature]}, ...}})
```
- 이 단계에선 각 노드들이 서로에게 자신이 관측한 값을 교환하는 과정이다.
- 자신의 관측값도 이에 포함시킨다. 모든 노드의 관측값과 그에 대한 증거인 서명을 교환한다.
- 비잔틴의 이보케이션 때문에 프리페어 하나만 있으면 안정성이 보장되진 않지만, 관측한 값을 서로 비교함으로 이 문제를 해결한다.
- 이것은 일종의 노드의 값의 차원을 증가시키는것이라 볼 수 있다.
- 비잔틴이 이 단에서 이보케이션을 해서 각 노드의 받는 정보를 다르게 할 수는 있다. 하지만 최종적인 안정성에는 영향을 주지 않는다.
- 사일런트, 타임아웃등으로 인하여 머지값을 받지 못하면 Unknown값으로 본다.
- 9] 정직 노드가 Prepare에서 낸 주장은 Merge를 거쳐 모든 정직 노드에게 동일하게 공유된다. 프리페어의 이보케이션은 머지와 Conflict 단계의 이보케이션 탐지로 막는다.
- O(n^2)의 시간 복잡도를 가진다. 비트 복잡도를 줄이려면, 해시 검증을 적용해 Fast-Path를 구현하는 방법이 있지만, 이는 로직상 변화를 안 주므로 구현체 단의 책임으로 정한다.

### Conflict
- 크게는, Merge의 세부 단에 속한다. 하지만 편의상 나눈다.
- 이 단은 모든 머지로 인한 값 교환이 끝나면 시작된다.
- 머지의 결과를 기반으로 각 노드의 최종 주장을 정리한다. 로컬에서 실행된다.
- 여기서, 컨플릭트가 나는 노드의 주장에, 서명이 있을 수 있다. 만약 비잔틴 노드가 만든 악의적인 주장이면, 이 시그니처는 거짓일 것이다.
- 만약 동일 노드에 대해 서로 다른 값을 가리키는 두 개 이상의 시그니처가 전부 옳다면, 그 노드는 이보케이션을 한 노드 말고는 다른 가능성이 없으므로 이 노드를 비잔틴으로 간주하고 무시한다. 이 노드의 최종 주장은 Unknown으로 처리한다.
- 정직 노드들이 관측한 서명 증거는 머지 단계에서 서로 공유되므로, 비잔틴 노드가 정직 노드들을 상대로 서로 다른 값을 서명해 보냈다면 모든 정직 노드는 이 노드가 이보케이션을 했음을 알 수 있다.
- 이보케이션 감지가 통과한 노드에 대해서, 정직한 서명을 포함한 주장을 그 노드의 최종 주장으로 받고, 옳은 서명이 없을시, 그 노드의 최종 주장을 Unknown으로 가정한다.
- 머지에서 비잔틴 노드가 이보케이션을 하더라도, 최대 f개의 비잔틴 노드만이 이를 방해할 수 있으므로 정직 노드의 주장을 망가뜨리거나 서로 다른 정직 노드가 상충하는 주장을 채택하게 만들 수 없다.
- 각 노드의 최종 주장이 모두 정리되면, 그중 과반(f+1)을 넘는 후보 값을 최종 Conflict 결과로 결정한다. 과반을 넘는 후보 값이 없으면 Reject로 결정한다.

### Commit
```
  Commit(proposeId, clientRequest, clientSigniture, nodeConsensusSignature) -> (nodeConsensusSignature)
  
  commitCert = {
    proposeId,
    clientRequest,
    clientSignature,
    {
      nodeId: nodeSignature, 
      ...
    },
  }
```
- 컨플릭트 단에서 결정된 결과를 기반으로 최종 커밋 여부를 확정한다.
- 서명 검증 실패, 타임아웃 미응답, 이보케이션 등으로 인해 특정 노드의 주장이 Unknown으로 처리된 경우, 어느 후보 값에도 투표하지 않은 것으로 간주한다.
- 단, Unknown이 발생하더라도 전체 쿼럼 임계값(Q=f+1)이나 f의 크기는 축소하지 않고 고정한다.
- 컨플릭트 결과로 유효한 후보 값(Reject가 아닌 값)이 결정되면, 정직 노드는 그 값을 서명한 뒤 서로에게 전파한다. 결과가 Reject인 경우에는 서명하지 않는다.
- 모든 정직 노드는 동일한 유효 후보 값을 도출하거나 Reject만 도출하며, 비잔틴 노드는 최대 f개이므로 과반(f+1)을 넘기지 못해 이중 값을 커밋할 수는 없다.
- Propose Id, Client Request, Client Signature등 클라이언트 요청에 필수적이며 공유되는 정보를 자신의 개인키로 서명후, 서명을 제공한다. 서명을 받는 노드는, 이 서명이 올바른지 검증한다.
- 특정 값에 대해 서로 다른 f+1개 이상의 유효한 커밋 서명이 수집되면 이는 유효한 커밋(Commit 인증서)으로 인정된다.
- 한 합의 안에는 후보값이 하나며, 비잔틴 노드 f개만으론, f+1개의 쿼럼을 도달할 수 없으므로 안정성이 보존된다.
- 정직 노드들이 서로 다른 두 값에 서명하는 일은 없으며 비잔틴 노드만으로는 f+1개의 서명에 도달할 수 없으므로, 상충하는 두 개의 커밋은 동시에 존재할 수 없다.
- 클라이언트는 f+1개의 커밋 서명(Commit 인증서)을 받아서 값의 정상 커밋 여부를 알 수 있다.
- 모든 노드가 서로에게 서명값을 주므로 통신 복잡도는 O(n^2)이다.

# MBQ Lemmas
## 상태 정의 및 공통 표기

다음 상태는 서로 다른 의미를 가진다.

- **`Unknown`**: 필요한 응답이나 유효한 증거를 확보하지 못했거나(Propose 미수신, 타임아웃, 침묵, 서명 검증 실패 등), 상충하는 서명(이보케이션)이 탐지되어 특정 후보를 지지할 수 없는 노드의 상태. 특정 후보의 지지로 계산하지 않으며, 이 상태만으로 결함 노드라고 단정하지도 않는다. 또한 `Unknown` 발생 여부와 무관하게 전체 쿼럼 임계값($Q=f+1$)은 축소하지 않는다.
- **`Reject`**: Conflict 단계에서 어떤 후보도 엄격한 과반($Q=f+1$)을 확보하지 못했을 때의 로컬 결정 결과. `Reject`를 도출한 정직 노드는 Commit 서명을 생성하지 않는다.

공통 표기:

- $n=2f+1$: 전체 노드 집합 $V$의 크기 ($\vert{}V\vert{}=2f+1$)
- $f$: 허용되는 결함(Byzantine, Crash, Omission) 노드 수의 상한
- $Q=f+1$: 엄격한 과반 쿼럼 크기
- $H$: 정직 노드의 집합 ($\vert{}H\vert{}\ge f+1$)
- $F$: 결함 노드의 집합 ($\vert{}F\vert{}\le f$, $H\cap F=\emptyset$, $H\cup F=V$)
- $\mathcal{V}$: 유효한 클라이언트 서명이 검증된 후보 요청 값들의 집합
- $P_k\in\mathcal{V}\cup\{\text{Unknown}\}$: 정직 노드 $k\in H$가 Prepare 단계에서 생성한 자신의 주장 (Propose를 정상 수신한 경우 해당 요청 값 $v\in\mathcal{V}$, Propose를 받지 못하고 유효한 클라이언트 서명이 포함된 Prepare를 통해 합류한 경우 `Unknown`)
- $E_k(v)=(v,\sigma_k(v))$: 노드 $k\in V$가 현재 합의 인스턴스(`proposeId`)의 후보 값 $v\in\mathcal{V}$에 대해 생성한 Prepare 주장과 유효한 노드 서명의 쌍 (서명 $\sigma_k(v)$는 합의 인스턴스 및 단계 정보를 포함하여 다른 단계나 요청에 재사용될 수 없음)
- $M_i$: 정직 노드 $i\in H$가 Prepare 및 Merge 단계 마감 기한까지 수집한 모든 노드의 서명 증거 및 관측 보고 집합
- $c_i(k)\in\mathcal{V}\cup\{\text{Unknown}\}$: 정직 노드 $i\in H$가 $M_i$를 바탕으로 Conflict 단계에서 확정한 노드 $k\in V$의 최종 Prepare 주장
- $C_i\in\mathcal{V}\cup\{\text{Reject}\}$: 정직 노드 $i\in H$가 도출한 최종 Conflict 결과

각 노드는 동일한 합의 인스턴스에서 최대 하나의 후보에 대해서만 유효한 지지자로 집계된다. 동일 노드의 상충하는 주장은 서로 다른 후보에 대한 독립적인 지지로 중복 집계하지 않는다.

## Lemma A — 상충 서명의 이보케이션 탐지

**주장.** 동일한 합의 인스턴스에서 동일 노드가 서로 상충하는 두 주장에 대해 유효한 서명을 생성했고, 두 서명이 검증자에게 제공되었다면 해당 노드의 이보케이션을 결정론적으로 탐지할 수 있다.

**증명.**

노드 $b\in V$가 동일한 합의 인스턴스에서 서로 다른 값 $v_1, v_2\in\mathcal{V}$에 대해 각각 유효한 서명 $\sigma_b(v_1)$, $\sigma_b(v_2)$를 생성했다고 하자. 단, $v_1\ne v_2$이다.

$$v_1\ne v_2$$

서명은 위조할 수 없으며 두 서명은 동일한 노드 $b$의 공개키로 검증된다. 정직 노드는 동일한 합의 인스턴스에서 단일 값에 대해서만 서명을 생성하므로, 서로 다른 두 값에 대한 유효 서명 쌍 $(\sigma_b(v_1),\sigma_b(v_2))$의 존재는 노드 $b\in F$가 이보케이션을 수행했음을 입증한다. 따라서 두 서명을 확보한 검증자는 이를 비교하여 해당 노드의 이보케이션을 즉시 탐지하고 해당 노드의 주장을 `Unknown`으로 무효화할 수 있다.

**결론.** 상충하는 유효 서명이 모두 확보되면 해당 노드의 이보케이션을 결정론적으로 탐지할 수 있다.

## Lemma B — Merge 이후 정직 노드의 증거 공유 및 노드별 주장의 양립 가능성

**주장.** 모든 정직 노드가 Prepare 단계에서 생성하거나 관측한 유효 서명 증거 집합을 Merge 단계에서 브로드캐스트하고, 정직 노드 사이의 메시지가 정해진 마감 기한 내에 전달된다고 하자. 각 정직 노드 $i\in H$가 수집한 Merge 결과 집합 $M_i$를 바탕으로 Conflict 단계에서 임의의 노드 $k\in V$의 최종 주장 $c_i(k)$를 다음 규칙으로 결정할 때:

1. **서명 검증 규칙:** $M_i$에 포함된 노드 $k$에 대한 보고 중, 유효한 클라이언트 서명 및 노드 $k$의 유효한 Prepare 서명 $\sigma_k(v)$가 확인되지 않는 허위 주장은 모두 배제한다.
2. **이보케이션 무효화 규칙:** $M_i$ 내에 동일 노드 $k$에 대하여 서로 다른 값을 가리키는 두 개 이상의 유효한 서명 증거 $E_k(v_1), E_k(v_2)$ ($v_1\ne v_2$)가 존재하면, 노드 $k$를 이보케이션을 수행한 비잔틴 노드로 간주하고 $c_i(k)=\text{Unknown}$으로 확정한다.
3. **최종 주장 확정 규칙:** 상충하는 유효 서명이 없고(이보케이션 감지 통과), 최소 $Q=f+1$개의 서로 다른 노드가 Merge에서 동일한 유효 서명 증거 $E_k(v)$를 보고한 경우에만 $c_i(k)=v$로 확정하며, 그렇지 않으면 $c_i(k)=\text{Unknown}$으로 확정한다.

위 조건 아래에서 비잔틴 노드가 Prepare 또는 Merge에서 이보케이션을 수행하더라도 정직 노드의 주장을 훼손할 수 없으며, 서로 다른 두 정직 노드 $i,j\in H$가 동일 노드 $k$에 대해 서로 상충하는 후보 값 $v_1\ne v_2$를 동시에 확정하는 것은 불가능하다.

**증명.**

먼저 서명은 위조할 수 없으므로, 비잔틴 노드가 Merge 단계에서 특정 노드 $k$의 주장을 임의로 조작해 보내더라도 유효한 서명 $\sigma_k(\cdot)$를 제시할 수 없어 **서명 검증 규칙**에 의해 배제된다. 특히 정직 노드 $h\in H$는 동일한 합의 인스턴스에서 최대 하나의 값 $P_h\in\mathcal{V}\cup\{\text{Unknown}\}$만 주장하며 상충 서명을 생성하지 않으므로, 비잔틴 노드가 Merge에서 이보케이션을 수행하더라도 정직 노드 $h$의 주장을 이보케이션으로 오판하게 만들거나 다른 값으로 변조할 수 없다.

임의의 정직 노드 $p\in H$가 Prepare 단계에서 노드 $k$의 유효 서명 증거 $E_k(v)=(v,\sigma_k(v))$를 관측했다면, $p$는 Merge 단계에서 이를 브로드캐스트한다. 동기 네트워크 가정에 의해 $p$의 Merge 메시지는 마감 기한 내에 모든 정직 노드에게 전달되므로 다음 포함 관계가 성립한다.

$$\forall p,i\in H,\qquad E_k(v)\in M_p\implies E_k(v)\in M_i$$

귀류법을 적용하기 위해 두 정직 노드 $i,j\in H$가 동일한 노드 $k\in V$에 대하여 서로 다른 유효 후보 값 $v_1, v_2\in\mathcal{V}$ ($v_1\ne v_2$)를 각각 다음과 같이 확정했다고 가정하자.

$$c_i(k)=v_1,\qquad c_j(k)=v_2\qquad(v_1\ne v_2)$$

**최종 주장 확정 규칙**에 의해, 노드 $i$는 최소 $f+1$개의 노드로부터 $E_k(v_1)$을 보고받았고, 노드 $j$는 최소 $f+1$개의 노드로부터 $E_k(v_2)$를 보고받았다.

결함 노드의 수는 최대 $f$개($\vert{}F\vert{}\le f$)이므로, 비잔틴 노드가 Merge 단계에서 이보케이션을 수행하더라도 최대 $f$개의 보고만 조작할 수 있다. 따라서 $E_k(v_1)$을 보고한 $f+1$개 이상의 노드 중에는 이를 Prepare에서 관측한 정직 노드 $p\in H$가 최소 1개 존재하고, $E_k(v_2)$를 보고한 $f+1$개 이상의 노드 중에도 이를 Prepare에서 관측한 정직 노드 $q\in H$가 최소 1개 존재한다.

정직 노드 $p$와 $q$가 Merge 단계에서 브로드캐스트한 증거 $E_k(v_1)$과 $E_k(v_2)$는 마감 기한 내에 모든 정직 노드에게 도달하므로, 노드 $i$와 $j$의 증거 집합은 모두 두 서명을 포함한다.

$$\{E_k(v_1),E_k(v_2)\}\subseteq M_i\cap M_j$$

따라서 Lemma A 및 **이보케이션 무효화 규칙**에 의해 노드 $i$와 $j$는 모두 $c_i(k)=\text{Unknown}$ 및 $c_j(k)=\text{Unknown}$으로 확정했어야 하며, 이는 가정에 모순이다.

**결론.** 임의의 노드 $k\in V$에 대하여 단일 후보 값 $v_k^*\in\mathcal{V}$가 존재하여, 모든 정직 노드 $i\in H$에서 확정된 노드 $k$의 주장은 다음을 만족한다.

$$\forall i\in H,\qquad c_i(k)\in\{v_k^*,\text{Unknown}\}$$

특히 $k\in H$인 정직 노드는 이보케이션을 수행하지 않고 모든 정직 노드($\vert{}H\vert{}\ge f+1$)에게 자신의 Prepare 상태 $P_k\in\mathcal{V}\cup\{\text{Unknown}\}$를 전달하므로, 모든 정직 노드 $i\in H$는 $c_i(k)=P_k$로 동일하게 확정한다.

## Lemma C — 결함 노드의 쿼럼 한계

**주장.** 결함 노드 수가 최대 $f$개이고 과반 쿼럼 및 Commit 인증서가 서로 다른 $Q=f+1$개 노드의 지지 또는 서명을 요구한다면, 결함 노드만으로 쿼럼을 충족하거나 Commit 인증서를 구성할 수 없다.

**증명.**

결함 노드의 수와 쿼럼 크기는 다음을 만족한다.

$$\vert{}F\vert{}\le f<f+1=Q$$

따라서 결함 노드만으로는 서로 다른 $f+1$개 노드의 지지나 서명을 확보할 수 없다.

`Unknown`은 특정 후보에 대한 지지로 계산되지 않는다. 또한 동일 노드의 상충하는 주장들을 서로 다른 후보에 대한 여러 개의 독립적인 지지로 계산하지 않는다. 이보케이션의 탐지는 Lemma A에 따른다.

`Unknown` 자체는 해당 노드가 결함 노드라는 증거가 아니며, `Unknown`이나 이보케이션이 발생했다는 이유로 $f$를 감소시키거나 쿼럼 임계값 $Q=f+1$을 변경하지 않는다.

**결론.** 결함 노드의 주장이나 서명만으로는 Conflict 단계의 과반 쿼럼이나 Commit 단계의 인증서 정족수를 충족할 수 없다.

## Lemma D — Commit 인증서의 안전성 (Safety)

**주장.** 모든 정직 노드 $i\in H$가 자신의 Conflict 결과 $C_i$가 유효한 후보 값($C_i\ne\text{Reject}$)일 때만 해당 값에 대해 Commit 서명을 생성한다면, 동일한 합의 인스턴스에서 서로 다른 값 $v_1\ne v_2$에 대한 유효한 Commit 인증서(`commitCert`)가 동시에 생성될 수 없다.

**증명.**

Lemma D에 따라 단일 합의 인스턴스에서 정직 노드들이 `Reject` 이외에 계산할 수 있는 유효 후보 값은 최대 하나($v^*\in\mathcal{V}$)뿐이다. 정직 노드는 자신이 도출한 유효 결과($C_i=v^*$)에 대해서만 `proposeId`, `clientRequest`, `clientSignature`를 묶어 자신의 개인키로 Commit 서명(`nodeConsensusSignature`)을 생성하고 전파하며, $C_i=\text{Reject}$인 경우에는 서명하지 않는다. 따라서 상충하는 값 $v'\ne v^*$ ($v'\in\mathcal{V}$)에 대해서는 어떠한 정직 노드도 Commit 서명을 생성하지 않는다.

상충하는 값 $v'$에 대한 유효한 Commit 인증서(`commitCert`)를 구성하려면 서로 다른 $Q=f+1$개 이상의 유효한 노드 Commit 서명이 필요하다. 그러나 정직 노드는 $v'$에 서명하지 않으므로, $v'$에 서명할 수 있는 노드는 결함 노드뿐이다.

따라서 Lemma C에 의해 확보 가능한 서명 수는 다음을 만족한다.

$$\#\operatorname{Signers}(v')\le \vert{}F\vert{}\le f<f+1=Q$$

이는 Commit 인증서의 정족수 요구 조건($f+1$개 이상)에 모순이다.

**결론.** 동일한 합의 인스턴스에서 서로 다른 값에 대한 두 유효 Commit 인증서가 동시에 생성될 수 없다.

Commit 인증서(`commitCert`)는 `proposeId`, `clientRequest`, `clientSignature` 및 서로 다른 $f+1$개 이상 노드의 `nodeConsensusSignature` 집합으로 구성되며, 클라이언트는 이를 수신·검증하여 요청의 정상 커밋 여부를 확정한다.

## Lemma E — Byzantine Proposer에 대한 안전성

**주장.** Byzantine Proposer가 요청을 일부 노드에게만 전달하거나, 노드마다 상충하는 요청을 전달하거나, 요청 전달을 중단하더라도, 앞선 Lemma의 조건 아래 서로 다른 값의 Commit 인증서를 생성할 수 없다.

**증명.**

클라이언트는 항상 정직하며 서명은 위조할 수 없으므로, Proposer는 클라이언트의 서명을 위조하여 서명된 요청 내용을 임의로 변조할 수 없다.

Proposer가 요청을 일부 정직 노드에게만 전달하거나 침묵할 경우, Propose를 직접 받지 못한 정직 노드는 올바른 클라이언트 서명이 포함된 Prepare 메시지를 수신하면 자신의 주장을 `Unknown`으로 설정한 채 이후 합의 단계(Prepare, Merge, Conflict, Commit)에 정상 참여한다. 또한 Proposer가 노드마다 상충하는 요청을 전달하거나 일부에게만 전달하더라도, 정직 노드가 생성 및 관측한 Prepare 결과는 Lemma B의 조건 아래 Merge 단계에서 모든 정직 노드에게 공유된다.

따라서 모든 정직 노드의 Conflict 결과는 Lemma D에 따라 단일 후보 값 $v^*$에 대하여 $C_i\in\{v^*,\text{Reject}\}$로 제한된다. 이어서 Lemma E에 의해 $v'\ne v^*$인 다른 값에 대한 Commit 인증서는 생성될 수 없다. (만약 정직 노드 중 일부만 $C_i=v^*$를 도출하고 나머지가 `Reject`를 도출하여 $f+1$개의 Commit 서명이 모이지 않는 거짓 실패(False Failure)가 발생하더라도, 상충하는 두 값이 커밋되는 안전성 위반은 결코 발생하지 않는다.)

**결론.** Byzantine Proposer의 선택적 전달, 이보케이션 또는 침묵만으로는 위 증명 조건 아래 Commit 안전성을 깨뜨릴 수 없다.

이 Lemma는 안전성에 관한 주장이다. 거짓 실패 등을 포함한 실패 시 클라이언트의 재시도를 통해 요청이 최종 성공한다는 진행성은 Lemma G에서 다룬다.

## Lemma F — 정직 Proposer 선택에 의한 유효성 및 확률적 진행성

**주장.** 정직한 Proposer가 선택된 합의 인스턴스에서는 클라이언트의 유효한 요청 값 $v$에 대해 반드시 유효한 Commit 인증서가 생성된다(유효성). 또한 클라이언트가 고정 1:1 매핑(IP Hashing 등)을 배제하고 각 재시도에서 이전 합의와 독립된 새 합의 인스턴스로 Proposer를 전체 $n=2f+1$개 노드 중 균등하고 독립적으로 선택할 때, 결함 노드가 최대 $f$개라면 각 시도에서 정직 Proposer가 선택되어 요청이 성공할 확률은 다음을 만족한다.

$$p\ge\frac{f+1}{2f+1}>\frac12$$

**증명.**

선택된 Proposer가 정직 노드($\in H$)라면, 클라이언트의 유효한 요청 $v$를 Propose 마감 기한 내에 모든 정직 노드에게 전달한다. 모든 정직 노드 $k\in H$는 동일한 Prepare 증거 $E_k(v)$를 생성하여 공유하므로($P_k=v$), Lemma B에 의해 모든 정직 노드 $i\in H$는 모든 $k\in H$에 대해 $c_i(k)=v$를 확정한다.

정직 노드의 수는 $\vert{}H\vert{}\ge f+1=Q$이므로, 모든 정직 노드 $i\in H$에서 $v$의 지지 집합 크기는 $\vert{}S_i(v)\vert{}\ge f+1$을 만족하여 $C_i=v$가 도출된다. 따라서 최소 $f+1$개의 정직 노드가 $v$에 대해 Commit 서명을 생성하므로 유효한 Commit 인증서(`commitCert`)가 단일 라운드 내에 결정론적으로 생성된다.

한편 전체 노드는 $2f+1$개이고 결함 노드는 최대 $f$개이므로, 고정 1:1 로드밸런싱을 배제한 균등 무작위 선택에서 정직 Proposer가 선택될 확률은 다음과 같다.

$$p=\frac{\vert{}H\vert{}}{2f+1}\ge\frac{f+1}{2f+1}>\frac12$$

각 재시도가 이전 합의와 무관한 새 합의 인스턴스(`proposeId`)에서 독립적으로 수행될 때, $k$회 이내에 적어도 한 번 정직 Proposer가 선택되어 요청이 성공할 확률은 다음을 만족한다.

$$P(\text{정직 Proposer 선택})\ge 1-\left(\frac{f}{2f+1}\right)^k$$

따라서 $k$가 증가할수록 정직 Proposer가 한 번 이상 선택될 확률은 $1$에 수렴한다.

**결론.** 정직 Proposer가 선택된 시도에서는 단일 라운드 내에 합의가 성립하며, 무작위 Proposer 선택 정책 아래에서는 매 시도에서 성공 확률이 절반을 초과하여 독립적인 재시도를 통해 성공 확률을 임의로 높일 수 있다.
